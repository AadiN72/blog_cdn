## Why the heck do I need a finite state machine?

This is a question that comes out of the mouth of any student learning a new topic. When the topic is forced on you, the question becomes louder. Since this one is self-imposed, I thought it was important to understand why I would need finite state machines in the first place.

![alt text](images-draft-1788507138809/why.webp)

Take a robot in a warehouse. It might have states like `IDLE`, `CHARGING`, `MOVING`, and `PLANNING`. These are the only states the robot can be in, and there are clean transitions between them: first it is `IDLE`, then a task comes in, so it is `PLANNING`; after planning, it starts `MOVING`.

We can add other states too, such as `OBSTACLE_STOPPED`, when sensors identify that the robot has been stopped. But we do not need every possible transition. Going directly from `MOVING` to `CHARGING`, for example, makes no sense.

## Okay, so what is an FSM?

To put it plainly:

> A finite state machine is a mathematical model of a robot's states, the actions inside those states, and the conditions for transitions between them.

![alt text](images-draft-1788507138809/fsm.png)

As the diagram shows, a finite state machine has a set of states and transitions between them based on different conditions. Each state can also have actions: the activity the robot performs while it is in that state.

Let's circle back to the warehouse robot, because it is an interesting problem with many possible states.

## What does this look like in code?

How about code? We can make it ridiculously simple like this:

```python
state = "IDLE"
retries = 0

while True:
    match state:
        # -------------------------
        # IDLE
        # -------------------------
        case "IDLE":
            event = input("IDLE event: ")

            match event:
                case "TASK_RECEIVED":
                    state = "PLANNING"

                case "BATTERY_LOW":
                    state = "CHARGING"

                case _:
                    print("Unknown event")

        # -------------------------
        # PLANNING
        # -------------------------
        case "PLANNING":
            event = input("PLANNING event: ")

            match event:
                case "ROUTE_FOUND":
                    state = "MOVING"

                case "PLANNING_FAILED":
                    state = "IDLE"

                case _:
                    print("Unknown event")

        # -------------------------
        # MOVING
        # -------------------------
        case "MOVING":
            event = input("MOVING event: ")

            match event:
                case "DESTINATION_REACHED":
                    state = "IDLE"

                case "OBSTACLE_DETECTED":
                    state = "OBSTACLE_DETECTED"

                case "BATTERY_LOW":
                    state = "CHARGING"

                case _:
                    print("Unknown event")

        # -------------------------
        # OBSTACLE DETECTED
        # -------------------------
        case "OBSTACLE_DETECTED":
            event = input("OBSTACLE_DETECTED event: ")

            match event:
                case "WAIT":
                    state = "WAITING"

                case "REROUTE":
                    state = "REROUTING"

                case _:
                    print("Unknown event")

        # -------------------------
        # WAITING
        # -------------------------
        case "WAITING":
            event = input("WAITING event: ")

            match event:
                case "PATH_CLEAR":
                    state = "MOVING"

                case "REROUTE":
                    state = "REROUTING"

                case _:
                    print("Unknown event")

        # -------------------------
        # REROUTING
        # -------------------------
        case "REROUTING":
            event = input("REROUTING event: ")

            match event:
                case "ROUTE_FOUND":
                    state = "MOVING"

                case "REROUTE_FAILED":
                    retries += 1
                    state = "WAITING"

                case _:
                    print("Unknown event")

        # -------------------------
        # CHARGING
        # -------------------------
        case "CHARGING":
            event = input("CHARGING event: ")

            match event:
                case "BATTERY_FULL":
                    state = "IDLE"

                case _:
                    print("Unknown event")

        # -------------------------
        # INVALID STATE
        # -------------------------
        case _:
            print(f"Invalid state: {state}")
            break

    print(f"Current state: {state}")
    print(f"Retries: {retries}")
    print()
```

We could make a more complex system using enums and structs to prevent invalid states and enforce proper transition conditions. Or we could use packages like `python-statemachine` or `xstate`.

## What happens when things go wrong?

For unexpected situations, we add conditions and states that account for them, then handle them with the actions in those states. In the machine above, the obstacle and replanning states do exactly that.

## Where FSMs start to suck

FSMs do not solve everything. They can fail pretty hard in situations like these:

- **State explosion:** making a state for every situation can create a stupidly large graph. Our example was getting pretty complex already.
- **Concurrency:** running multiple states is not possible when we always transition from one state to another; we cannot transition to two states at once.
- **Complex behaviours:** because the states need to be finite, we cannot model every complex behaviour neatly.
