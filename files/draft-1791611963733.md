## What is a behaviour tree?

*As always, let’s start with the what before getting into the fun stuff.*

> A behaviour tree is a hierarchical model for deciding what a system should do.

Instead of writing one massive block of logic, we break complex behaviour into smaller, reusable pieces.

Last week (*cough* month *cough*), we learnt about finite state machines (FSMs). With FSMs, we define states and the transitions between them. Behaviour trees approach the same problem a little differently: we organise conditions and actions into a hierarchy rather than explicitly defining every possible transition.

The useful part is that we can mix and match those conditions and actions to build increasingly complex behaviours.

### The building blocks

Here are the main components I’ve been working with:

| Node | What it does | Success? | Failure? | Running? |
| --- | --- | --- | --- | --- |
| Sequence | Runs its children in order | When all children return success | When any child returns failure | When a child is still running |
| Fallback | Tries its children as alternatives | When any child returns success | When all children fail | When a child is still running |
| Action | Performs a given activity | Depends on the activity | Depends on the activity | Depends on the activity |
| Condition | Checks a given condition | When the condition is true | When the condition is false | Not applicable |
| Retry | Retries its child until a limit is reached | When the child succeeds | When the retry limit is reached | While the child is still running |

One thing that clicked for me was that these nodes communicate using three possible statuses: **SUCCESS**, **FAILURE**, and **RUNNING**.

A sequence keeps moving through its children as long as they succeed. If one fails, the sequence fails. If one is still running, the sequence reports that it is running too.

A fallback works differently. It tries alternatives until one succeeds.

### Ticks

Behaviour trees are governed by something called *ticks*. A tick is essentially a command to evaluate the tree and determine what should happen next.

Each time the tree is ticked, it evaluates the relevant nodes and checks their statuses. Depending on the node, it might continue an existing action, try another branch, or react to a condition that has changed.

The tick frequency determines how often the tree gets a chance to respond to external stimuli. For a robot, this matters quite a bit: sensor readings change, obstacles appear, batteries drain, and tasks can take multiple ticks to complete.

Rather than deciding everything once and hoping for the best, the tree can keep evaluating what needs to happen.

I find this an interesting way to think about robot behaviour.

With the FSM, I was thinking: *which state am I in, and where can I go next?*

With the behaviour tree, I’m thinking more in terms of: *what needs to happen, and what should I try if that doesn’t work?*

The underlying robot tasks haven’t changed. We’re still dealing with charging, planning routes, navigating, and waiting. What has changed is how we organise the decisions.

## Implementation

How would we actually implement this? I wanted to look at two approaches: using BehaviourTree.CPP with C++, and writing the same sort of decision-making logic directly in Python.

### Using BehaviourTree.CPP

With BehaviourTree.CPP, we can define the structure of our tree using XML. For our robot, that would look something like this:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<root BTCPP_format="4" main_tree_to_execute="RobotTree">
  <BehaviorTree ID="RobotTree">
    <ReactiveFallback>
      <Sequence>
        <BatteryLow/>
        <ChargeBattery/>
      </Sequence>

      <Sequence>
        <TaskReceived/>
        <Fallback>
          <Sequence>
            <RouteAvailable/>
            <Navigate/>
          </Sequence>
          <Sequence>
            <PlanRoute/>
            <Navigate/>
          </Sequence>
        </Fallback>
      </Sequence>

      <Idle/>
    </ReactiveFallback>
  </BehaviorTree>
</root>
```

The XML describes how the different nodes are connected.

At the top, we have a `ReactiveFallback`. This lets us prioritise different behaviours and recheck higher-priority branches on subsequent ticks.

Our priorities are fairly straightforward:

1. If the battery is low, charge it.
2. If a task has been received, navigate towards the destination.
3. If neither applies, remain idle.

Within navigation, we first check whether a route is available. If it isn’t, we try planning one before navigating.

This is where sequence and fallback nodes start to make sense. We can combine relatively simple checks and actions to describe more complicated behaviour.

### The C++ implementation

The XML defines the structure, but we still need to implement what each node actually does. In C++, that could look like this:

```cpp
#include <behaviortree_cpp/bt_factory.h>
#include <iostream>
#include <memory>
#include <string>

using namespace BT;

struct Robot
{
    int battery = 100;
    int position = 0;
    int destination = 5;

    bool task_received = true;
    bool route_available = false;
    bool obstacle = false;
    bool path_clear = true;
    bool destination_reached = false;
};

// Long-running navigation action
class Navigate : public StatefulActionNode
{
public:
    Navigate(const std::string& name,
             const NodeConfig& config,
             Robot& robot)
        : StatefulActionNode(name, config),
          robot_(robot)
    {}

    static PortsList providedPorts()
    {
        return {};
    }

    NodeStatus onStart() override
    {
        return onRunning();
    }

    NodeStatus onRunning() override
    {
        if (robot_.destination_reached)
        {
            robot_.task_received = false;
            robot_.route_available = false;
            return NodeStatus::SUCCESS;
        }

        if (robot_.obstacle)
        {
            std::cout << "REROUTING\n";

            if (!robot_.path_clear)
            {
                std::cout << "WAITING\n";
                return NodeStatus::RUNNING;
            }

            robot_.obstacle = false;
            std::cout << "ROUTE_FOUND\n";
        }

        std::cout << "MOVING\n";
        robot_.position++;
        robot_.battery -= 5;

        if (robot_.position >= robot_.destination)
        {
            robot_.destination_reached = true;
            robot_.task_received = false;
            robot_.route_available = false;

            std::cout << "DESTINATION_REACHED\n";
            return NodeStatus::SUCCESS;
        }

        return NodeStatus::RUNNING;
    }

    void onHalted() override
    {
        std::cout << "Navigation halted\n";
    }

private:
    Robot& robot_;
};

// Long-running charging action
class ChargeBattery : public StatefulActionNode
{
public:
    ChargeBattery(const std::string& name,
                  const NodeConfig& config,
                  Robot& robot)
        : StatefulActionNode(name, config),
          robot_(robot)
    {}

    static PortsList providedPorts()
    {
        return {};
    }

    NodeStatus onStart() override
    {
        return onRunning();
    }

    NodeStatus onRunning() override
    {
        std::cout << "CHARGING\n";
        robot_.battery += 20;

        if (robot_.battery >= 100)
        {
            robot_.battery = 100;
            return NodeStatus::SUCCESS;
        }

        return NodeStatus::RUNNING;
    }

    void onHalted() override {}

private:
    Robot& robot_;
};

int main()
{
    Robot robot;
    BehaviorTreeFactory factory;

    factory.registerSimpleCondition(
        "BatteryLow",
        [&robot](TreeNode&)
        {
            return robot.battery < 20
                ? NodeStatus::SUCCESS
                : NodeStatus::FAILURE;
        });

    factory.registerSimpleCondition(
        "TaskReceived",
        [&robot](TreeNode&)
        {
            return robot.task_received
                ? NodeStatus::SUCCESS
                : NodeStatus::FAILURE;
        });

    factory.registerSimpleCondition(
        "RouteAvailable",
        [&robot](TreeNode&)
        {
            return robot.route_available
                ? NodeStatus::SUCCESS
                : NodeStatus::FAILURE;
        });

    factory.registerSimpleAction(
        "PlanRoute",
        [&robot](TreeNode&)
        {
            std::cout << "PLANNING\n";
            robot.route_available = true;
            return NodeStatus::SUCCESS;
        });

    factory.registerSimpleAction(
        "Idle",
        [](TreeNode&)
        {
            std::cout << "IDLE\n";
            return NodeStatus::SUCCESS;
        });

    factory.registerNodeType<Navigate>(
        "Navigate", robot);

    factory.registerNodeType<ChargeBattery>(
        "ChargeBattery", robot);

    auto tree = factory.createTreeFromFile(
        "robot_tree.xml");

    for (int tick = 0; tick < 20; ++tick)
    {
        std::cout << "\nTick " << tick << "\n";

        if (tick == 3)
        {
            robot.obstacle = true;
            robot.path_clear = false;
        }

        if (tick == 5)
        {
            robot.path_clear = true;
        }

        tree.tickOnce();
    }

    return 0;
}
```

There’s quite a bit going on here, but the important part is how the tree connects to the robot’s actual behaviour.

The `Robot` struct stores information such as the battery level, current position, destination, and whether an obstacle has been detected.

We then create actions such as `Navigate` and `ChargeBattery`. Both inherit from `StatefulActionNode`, which is useful for actions that don’t finish immediately.

For example, navigating to a destination takes time. Instead of returning `SUCCESS` straight away, the navigation node returns `RUNNING` while the robot is moving or waiting for a clear path. Once the destination is reached, it returns `SUCCESS`.

The conditions are simpler. `BatteryLow` checks whether the battery has dropped below 20%, while `TaskReceived` and `RouteAvailable` check their corresponding flags.

Finally, we register all these nodes with the factory, load our XML tree, and start ticking it.

I’ve also added a small obstacle simulation. At tick 3, an obstacle appears and the path becomes blocked. At tick 5, the path clears again. This lets us see how the navigation action responds when something changes during execution.

One detail worth keeping in mind is that the charging condition here is only checked against the 20% threshold. Once the battery rises above that threshold, the reactive tree can move on to another branch, even if charging hasn’t reached 100%.

So this is a useful starting point, but the charging behaviour would need some refinement if we wanted the robot to finish a full charging cycle.

### Or we could use Python

We can also implement similar behaviour directly in Python without relying on an external behaviour tree library.

```python
from enum import Enum
import time


class Status(Enum):
    SUCCESS = 1
    FAILURE = 2
    RUNNING = 3


class Robot:
    def __init__(self):
        self.battery = 100
        self.task_received = False
        self.route_available = False
        self.obstacle = False
        self.path_clear = True
        self.destination_reached = False
        self.position = 0
        self.destination = 5
        self.state = "IDLE"

    def plan_route(self):
        self.state = "PLANNING"
        print("Planning route...")
        self.route_available = True
        return Status.SUCCESS

    def navigate(self):
        if self.destination_reached:
            self.task_received = False
            self.route_available = False
            self.state = "IDLE"
            return Status.SUCCESS

        if self.obstacle:
            self.state = "REROUTING"
            print("Obstacle detected! Rerouting...")

            if self.path_clear:
                self.obstacle = False
                print("New route found")
            else:
                self.state = "WAITING"
                print("Reroute failed. Waiting...")
                return Status.RUNNING

        self.state = "MOVING"
        self.position += 1
        self.battery -= 5
        print(f"Moving: {self.position}/{self.destination}")

        if self.position >= self.destination:
            self.destination_reached = True
            print("Destination reached!")

        return Status.RUNNING

    def charge(self):
        self.state = "CHARGING"
        self.battery = min(100, self.battery + 20)
        print(f"Charging: {self.battery}%")
        return Status.RUNNING

    def idle(self):
        self.state = "IDLE"
        print("Robot idle")
        return Status.RUNNING

    def tick(self):
        # Priority 1: battery safety
        if self.battery < 20 or self.state == "CHARGING":
            if self.battery < 100:
                return self.charge()

        # Priority 2: task execution
        if self.task_received:
            if not self.route_available:
                result = self.plan_route()
                if result != Status.SUCCESS:
                    return result
            return self.navigate()

        # Priority 3: idle
        return self.idle()


if __name__ == "__main__":
    robot = Robot()
    robot.task_received = True

    for tick in range(15):
        print(f"\n--- Tick {tick} ---")

        if tick == 3:
            robot.obstacle = True
            robot.path_clear = False

        if tick == 5:
            robot.path_clear = True

        robot.tick()
        time.sleep(0.5)
```

The Python version is a little easier to follow because everything is written directly inside the `Robot` class.

We still have the same basic ideas: statuses, conditions, actions, and ticks. The `tick()` method checks the robot’s priorities in order. If the battery needs charging, we charge it. Otherwise, if there’s a task, we plan a route if necessary and navigate. If there’s nothing to do, the robot remains idle.

The navigation logic also handles obstacles. When the path is blocked, the robot waits rather than continuing to move. Once the path clears, it can resume.

There is one important distinction, though: **this isn’t a full behaviour tree implementation**.

We’re manually writing the decision-making logic using `if` statements, rather than building a reusable hierarchy of sequence, fallback, and action nodes. It demonstrates similar behaviour, but we lose some of the modularity that makes behaviour trees interesting in the first place.

The two examples also handle charging slightly differently. The Python version keeps charging once it enters the `CHARGING` state, while the C++ tree rechecks the low-battery condition.

That difference is a useful reminder that even when two implementations look similar, small decisions about how conditions are evaluated can change the robot’s behaviour.

## Where do behaviour trees start to suck?

Like FSMs, behaviour trees aren’t a one-size-fits-all solution. They work exceedingly well in some situations and can become a bit of a headache in others.

### Complex trees get messy

As the number of behaviours increases, the tree can become a deeply nested mess of:

`Fallback → Sequence → Action → Fallback → Sequence...`

And that’s before adding retries, recovery behaviours, and all the other things a real robot might need.

The hierarchy helps organise complexity, but it doesn’t magically make complexity disappear.

### Remembering previous actions

Behaviour trees don’t automatically remember everything that happened during previous ticks.

Depending on how the nodes are implemented, actions may be restarted or evaluated again when the tree is ticked. This can become a problem when an action should only happen once, or when the robot needs to remember that it has already completed part of a task.

We can manage this by storing state and using appropriate node types, but it’s something we need to think about rather than assume the tree handles for us.

### Debugging can be difficult

A small behaviour tree is fairly easy to understand. A large one with several nested branches, conditions, and recovery actions? Not quite as pleasant.

When something goes wrong, figuring out which node returned failure, which branch was selected, and why an action restarted can become tricky.

So while behaviour trees give us a nice way to structure decision-making, they also introduce their own debugging challenges.

## What I learnt

The biggest thing I learnt this week is that behaviour trees and finite state machines are two different ways of organising the same underlying problem: deciding what a robot should do next.

FSMs make the states and transitions explicit. Behaviour trees focus more on composing conditions and actions into a hierarchy.

Neither is automatically better.

For a small system with a handful of clearly defined states, an FSM can be perfectly reasonable. But as the number of tasks, conditions, and recovery behaviours grows, I can see why behaviour trees become attractive.

What I particularly like is the idea of building complicated robot behaviour out of smaller pieces that can be reused.
